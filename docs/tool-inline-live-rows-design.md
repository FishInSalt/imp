# Tool inline live rows: design for independent review

Status: **draft — awaiting independent adversarial review**. This document
changes no runtime behavior. No commit to `main`, merge, provider request,
deployment, or release is part of this work.

Baseline: `412a2c8` (`main`). Branch: `docs/tool-inline-live-rows`.

## 0. Decision history (owner, 2026-10-02)

- Owner report (dogfood): while a top-level tool runs, the transcript shows
  the call header and the activity region repeats the call — the command text
  appears twice. Question: should tools follow `#task-inline-live-rows` (live
  state in the call's own record entry)?
- The owner then proposed the compact alternative "timer on the call line"
  (`● bash  npm run build --watch · 12s`, ticking to `· 13s`).
- After a tradeoff round (header-suffix engineering cost; grammar consistency
  with the shipped task rows) the owner agreed to the live-row form first
  ("后者可以更稳定和醒目点，我同意") and left the header suffix as a possible
  later migration. This document implements the live-row form and records the
  suffix rejection in §9.

## 1. Problem and observed cause

While a top-level non-task tool call (e.g. `bash`) runs, the screen shows
(generated by the real components; the running row is two lines today):

```
● bash  npm ci --silent ✓ 8.4s
  ⎿ added 412 packages in 8s
● bash  npm run build --watch          ← transcript input fold (appended at tool_start)
⠋ running 12s                          ← activity region, line 1 (status)
bash npm run build --watch             ← activity region, line 2 (args label)
```

Two causes:

1. **Structural.** The call's input fold is appended to the transcript at
   `tool_start` (`src/repl/tool-presentation.ts:662-669`), while the live state
   is a row group in the activity container, a sibling added below the whole
   transcript (`src/repl/shell.ts:340-341`). Both surfaces exist at the same
   time by construction.
2. **Content.** The activity row group is two lines — status
   (`⠋ running Ns`) and the wrapped args label (`name label`, shell-built at
   `src/repl/shell.ts:705-709`) — and the label repeats the transcript header.
   The region's status line is the only place that carries the elapsed time;
   the transcript header has none while running. After the call settles the
   duplication disappears (the header gains `✓/✗ + time`, the region row is
   removed).

`#task-inline-live-rows` already solved this shape of problem for `task` calls
by routing their live rows into the call's own fold; this batch extends the
same treatment to every top-level non-task tool.

## 2. Decision

Move each top-level non-task tool call's live state into its own input fold as
a single dim row `└─ running Ns` (seconds omitted at zero), cleared when the
call settles; the activity region stops painting tool rows. Reuse the
`#task-inline-live-rows` channel (fold live-row slot, transcript id map,
publisher resolver, 120ms ticker, per-second content dedup) rather than
building a new one. Gate semantics extend D10's pull-based suppression to the
row push (§5.3). The seam gains call-generic names (§5.5).

## 3. Current integration boundaries (verified on `412a2c8`)

Producer / snapshot:

- `ReplMachine.trackActivity` (`src/repl/repl.ts:1224`) runs before
  `renderer.event` for every event (`src/repl/repl.ts:756-763`).
- Top-level non-task `tool_start` stores an `ActivityToolLine`
  (`{id, name, label, startedAtMs}`, `src/repl/line-input.ts:166-174`) in
  `activityTools` (`src/repl/repl.ts:1310-1315`); `tool_end`/`tool_settled`
  delete it (`src/repl/repl.ts:1322`). `pushActivity` copies
  `{phase, tools, agents}` to the shell (`src/repl/repl.ts:1351-1366`).
- Non-task tools are never concurrency-safe (only `task` is,
  `src/core/tools/task.ts:354`), so non-task calls run one at a time on the
  serial path (`src/core/loop.ts:457-461`); at most one entry exists in
  `activityTools` at any moment (the map handles N regardless).
- `tool_start` precedes the gate in both execution paths (serial:
  `src/core/loop.ts:458-459` then the gate at `:656`; chunk phase 1:
  `:504-520`). A snapshot can therefore hold a call that is not executing
  (picker open).

Shell:

- `TuiShell.renderActivity` (`src/repl/shell.ts:660`) paints the tools loop at
  `:702-711` (status + label rows via `ToolActivity`), inside the D10 guard
  `if (this.selector === null)`; the agents loop at `:716-748` already routes
  rows to `transcript.setTaskLiveRows`. `setSelector` (`:647`) repaints on
  every transition — D10's suppression is pulled, not pushed.

Channel (reused as-is):

- `ToolBlockFold.setLiveRows` (`src/repl/components/tool-block.ts:178-197`);
  live rows splice after the header chain at `headerEnd` (`:573`, `:767`);
  the render cache key includes `liveRevision` (`:212-219`); input folds only
  (a result fold can never carry live rows).
- `TranscriptSink.inputFoldById` (`src/repl/transcript.ts:64`),
  `taskLiveRowsResolver` (`:78`), the append callback's displaced-fold clear
  (`:103-104`) and resolver pull (`:108`), `setTaskLiveRows` (`:169-173`),
  `clear()` (`:127`).
- `TuiShell` installs the resolver in `start()` (`:300-301`) and unbinds it
  behind the ownership guard in `stopTerminal()` (`:1223-1224`). The 120ms
  ticker recomputes rows while the phase is not `idle` and pushes only content
  that changed.

## 4. Goals / non-goals

Goals:

1. A running top-level tool's live state renders exactly once, attached to its
   own call entry (`└─ running Ns` under the header).
2. The activity region paints no tool rows; the phase rows (`thinking`,
   `compacting`) stay, and a picker open during a gate must not claim
   `running` (D10 semantics preserved).
3. The settled transcript, replay, print mode, and the legacy shell stay
   byte-identical.
4. Existing channel guarantees carry over: used-id safety, clear on
   end/idle/interrupt/exit, no live rows in replay, resolver pull for a fold
   created after the row was published.

Non-goals:

- The header-suffix form (owner's alternative; §9 records the rejection).
- Any change to task live rows or their shape.
- Child tool live rows: child calls still reach the screen only through their
  task's live rows (`lastTool` / `toolCount`), never as their own fold or row.
- Streaming tool output (a separate batch; see §5.6).
- Snapshot shape changes beyond naming.

## 5. Design

### 5.1 Row shape

One row per running tool call: `└─ running`, then `└─ running 1s`, …,
`└─ running 9999+s` (floor; `activityCount` semantics; zero omitted, matching
today's region `elapsed()`). No name and no args label — the header directly
above carries both; this is the duplication being removed. No spinner frames:
the ticking seconds are the liveness signal, identical to the task rows'
cadence, and avoid per-frame fold-cache churn (`liveRevision` changes only
when the row text changes, i.e. about once per second).

The row renders through the existing live-row path: `DIM` + `activityText` +
`ellipsize`, spliced between the header and any body/result rows, and it
ignores `expanded` (a Ctrl+O expansion while running neither hides nor
duplicates it).

### 5.2 Routing

In `renderActivity`, build a single `nextLiveRows: Map<string, readonly
string[]>`:

- tools (only when `this.selector === null`, §5.3): `key = tool.id`,
  `rows = ["└─ running…"]` computed from `tool.startedAtMs` against `now`;
- agents: unchanged aggregation (`parentKey = agent.taskToolId ||
  agent.sourceId || ""`, ordinals, three-row groups).

Push changed rows via `transcript.setCallLiveRows(key, rows)` (renamed, §5.5),
push `null` for keys that left the map, and on the `idle` branch clear every
tracked key and reset `taskOrdinals` (as today). Tools are no longer added to
the activity container; the now-unused `add()` helper and the `elapsed()`
helper in `renderActivity` are deleted. `activityRows` / `ToolActivity` stay:
the defensive zero-parent agent branch (`taskToolId === ""`) still uses them.

### 5.3 Gate / picker semantics

No new signal. Tool rows are computed only when `selector === null`, mirroring
D10's paint-time rule; `setSelector` repaints both edges, so:

- picker opens → the row is suppressed (nothing executes; no false
  `running` claim);
- picker closes after approval → the row appears while the call is still in
  the snapshot;
- denied + blocked → the call leaves the snapshot on `tool_end` inside the
  same event chain that produces the block result; at most a sub-frame window
  exists before the next paint (16ms render throttle), so no observable flash
  is expected.

Accepted, recorded consequences:

1. The elapsed counter accumulates from `tool_start` (gate wait included),
   identical to today's region row and to the task rows; the settled `✓/✗`
   duration remains the execution-only measurement (`#tool-settle`).
2. A picker opened mid-run by a command like `/model` hides a genuinely
   running tool row — D10 already accepted this for the region (recorded in
   `docs/confirm-prompt-design.md` §15, "`/model` … hides real activity
   rows"); this batch inherits, does not change, that behavior.

### 5.4 Lifecycle

- settle (`tool_end` / `tool_settled`): the key leaves the snapshot, so the
  next `renderActivity` pushes `null`. The header update (`✓/✗ + time`) and
  the result fold are produced by `sink.end` in the same event handling —
  one frame, no intermediate state.
- idle / `clearActivity` / interrupt / exit: all live rows cleared (idle
  branch), exactly as task rows are today.
- reused tool_call ids (providers may synthesize `call_${index}`): the
  existing displaced-fold clear in the append callback (`transcript.ts:103-104`)
  covers any input fold; the pushed row addresses the newest fold only.
- fold created after the row was published: the resolver pull
  (`transcript.ts:108`) covers it, unchanged.

### 5.5 Naming (mechanical rename)

The seam is now call-generic, so rename it:

- `TranscriptSink.setTaskLiveRows` → `setCallLiveRows` (`transcript.ts:169`);
- `TranscriptSink.taskLiveRowsResolver` → `callLiveRowsResolver`
  (`transcript.ts:78`);
- `TuiShell.taskLiveRows` → `callLiveRows` (`shell.ts:234`).

`ToolBlockFold.setLiveRows` keeps its name (the two-layer distinction the task
batch's §5.2 established). Comments referencing task-only semantics are
updated. The historical `docs/task-inline-live-rows-design.md` is not edited
(it records the state at its baseline).

### 5.6 Unchanged on purpose

- Task rows and their three-line shape; the ordinal machinery.
- Activity phase rows (`thinking` / `compacting`) and the D10 picker
  suppression of tool rows — extended, not replaced.
- The `ToolActivity` component and its defensive zero-parent path.
- The snapshot field set: `ActivityToolLine.name` / `.label` are no longer
  used for display, but they stay as accurate descriptors in the machine→shell
  contract; trimming them is churn without display benefit (open point §8.5).
- Print mode, legacy shell, replay bytes: no live-row path exists there.
- Streaming tool output: imp does not stream output today — the result lands
  once at settle, so "timer vs output" never coexist on screen. A future
  streaming feature sits below the live row's splice point by construction and
  needs its own batch (truncation, cadence, scroll, expansion semantics).

## 6. Frames (timeline)

Running (12s), proposed:

```
● bash  npm ci --silent ✓ 8.4s
  ⎿ added 412 packages in 8s
● bash  npm run build --watch
└─ running 12s
```

Settled (30.2s), same in both worlds:

```
● bash  npm ci --silent ✓ 8.4s
  ⎿ added 412 packages in 8s
● bash  npm run build --watch ✓ 30.2s
  ⎿ webpack compiled successfully
    watching for changes...
```

Interrupted: the row is cleared, the header keeps today's finalize form
(`● bash · interrupted (no result)  npm test`).

Grammar comparison with the shipped task rows (`└─ pending #1 scout 12s` /
prompt / `N tool starts · last: …`): same visual grammar — live state as dim
`└─` rows under the call's own header; the tool's state is simply one row
lighter.

## 8. Risks and open points for the reviewer

1. **Transcript re-render cost.** Live rows now render in the transcript for
   every tool call; the task batch accepted this cost with the
   content-dedup + `liveRevision` bound (its §8.1). Same acceptance here, one
   second cadence.
2. **Scroll-away.** A long-running tool's header (with its live row) can
   scroll off the visible area; the activity region was always visible. This
   is the recorded `#task-inline-live-rows` tradeoff, extended to tools; call
   it out in the changelog.
3. **Gate window / `/model` hiding a running row.** §5.3: inherited D10
   acceptance, not a regression. Reviewer to confirm this reading.
4. **Rename churn.** Mechanical, zero behavior change claimed; reviewer to
   verify (no residual `taskLiveRows` usages, comments updated).
5. **`name` / `label` fields now display-unused.** Keep (contract descriptors)
   vs trim (dead data). This document keeps them; reviewer may object.
6. **Payload-preview test removal** (`:4793`): confirm the coverage it
   provided (label sanitized once per payload) is not needed elsewhere; after
   this batch the row carries no label, so the concern mostly evaporates for
   tools.
7. **Elapsed includes gate wait.** Matches today's region row and the task
   rows; the settled duration stays execution-only. Reviewer to confirm
   consistency is preferable to a new "executing" signal (which would require
   a new event — explicitly avoided).
8. **Mixed batches.** `#task-inline-live-rows` §8.8 recorded that a batch
   mixing `task` and a non-task tool spans two regions while running. With
   this batch both call types render in the transcript, which removes that
   inconsistency — a check the reviewer should confirm against the current
   code.

## 9. Alternatives considered

- **Header suffix** (`● bash  npm run build --watch · 12s`, owner-floated).
  Visually more compact; rejected for engineering cost and consistency:
  the completion suffix lives in the fold's invariant-heavy region (I1–I6:
  width reservation from the first row's wrap budget, 8-column floor,
  `summaryVisible` accounting, four header emission branches,
  `src/repl/components/tool-block.ts:494-556`); a running state would mutate
  the header every second, change the reserved width as digit counts grow
  (9s→10s→100s re-ellipsizes a long command), and require parallel
  push/cache machinery. Owner agreed to keep it as a possible later migration
  on top of this batch's routing work.
- **Unify task to the suffix.** Rejected: task live state is compound — a
  full-prompt row, the `N tool starts · last: …` progress row, and the `#N.n`
  discriminator; a suffix slot cannot carry them without dropping shipped
  signals (would relitigate `docs/task-live-display-design.md` §2 and the
  task batch).
- **Status quo** (duplication). Rejected: owner-reported; the command text
  renders twice for the whole duration of every tool call.
